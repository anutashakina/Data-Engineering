## Этап 3. Приостановка лидера без защиты

### 3.1. Две копии координатора и сессия 10 секунд

Предыдущий расчёт использовал MapReduce и сравнение с DuckDB. В ДЗ № 4 добавлен
[координатор](../src/zk_coordinator.py), использующий исходные `map_chunk` и `save_counts`.
Сохраняется исходное условие: роль «Программист, разработчик», C/C++ в названии,
исходная нормализация, подсчёт наборов размера 1, 2, 3, включая требуемые пары.
Из исходного CSV выделено **3676** подходящих вакансий.

Два отдельных процесса A и B используют `Kazoo Lock`: эфемерные последовательные
узлы и наблюдение за предшественником. Победитель атомарно увеличивает `/epoch`.
Чекпоинт содержит обработанное количество вакансий, накопленные частоты и хеш входа.
Неизменяемый файл закрывается до публикации указателя на него; при восстановлении
проверяются SHA-256 файла и принадлежность входному набору.
Публикация чекпоинта в ZooKeeper всегда проверяет эпоху транзакцией, поэтому старый
процесс не может откатить прогресс нового лидера даже в сценарии без защиты результата.

[Сценарий проверки](../src/check_zookeeper.py) дожидается чекпоинта A на 600 вакансиях,
запускает B, приостанавливает **весь процесс A**, включая потоки heartbeat, на 40 секунд
через `psutil.Process.suspend()`, затем вызывает `resume()`.
Пауза не моделируется обычным `sleep` в координаторе: такой sleep оставил бы heartbeat работающим.
Между порциями есть задержка 0,5 с, чтобы успеть приостановить процесс посреди расчёта.

B становится лидером после удаления эфемерного узла A при истечении сессии,
получает эпоху 2, читает чекпоинт с offset 600 и обрабатывает остаток.
A после возобновления фиксирует `Session has expired`, `LOST` и продолжает локальное
вычисление. Такое поведение оставлено намеренно для проверки устаревшей записи.

### 5.2. Почему три сервера, а не два и не четыре?

Для принятия решений нужна большая половина серверов. Любые два большинства
пересекаются, поэтому две разошедшиеся части ансамбля не могут одновременно
принимать независимые записи. У двух серверов большинство — два: потеря любого
останавливает запись. У трёх большинство — два: один сервер может отказать.
У четырёх большинство — три: допустим всё ещё только один отказ, хотя серверов
и обменов стало больше. Поэтому три — минимальное число голосующих серверов
для сохранения работы после одного отказа. Для двух отказов нужны пять.

### 5.3. Почему эпоху проверяет получатель записи, а не только ZooKeeper?

После паузы старый процесс может продолжить работу с уже устаревшим знанием «я лидер».
ZooKeeper удалит его эфемерный узел, но не остановит процесс и не запретит запись
в сторонний файл, БД или API. Даже проверка лидерства перед отправкой оставляет
промежуток: между проверкой и записью лидер может смениться.

Поэтому получатель должен отвергать старые эпохи в той же атомарной операции,
в которой принимает результат. В этой работе получатель — функция `receive_result`,
а опубликованный ресурс — указатель `/result` в ZooKeeper. Она выполняет `check`
версии `/epoch` и `set_data /result` в одной транзакции. У A сохранена версия эпохи 1,
после избрания B текущая версия 2; `check` возвращает `BadVersionError`, и указатель
вообще не изменяется. Здесь механизм проверки выполняет ZooKeeper, потому что сам
ресурс расположен в нём. Для результата в отдельной БД проверять эпоху и менять
результат должна сама БД в одной транзакции; отдельный предварительный запрос к
ZooKeeper такую гарантию не даёт.

## Итоги и границы эксперимента

Автоматически проверены роли, доступность записи при одном отказе и недоступность
при двух, удаление эфемерного узла, ненулевой offset восстановления, SHA-256 результатов,
число публикаций, версии указателя, имя итогового владельца и `BadVersionError`.
Запуск сценария завершился с кодом 0. Технические результаты подтверждены текстовыми
журналами. Для завершения оформления остаётся вставить скриншоты и опубликовать материалы.
Скринкаст можно приложить дополнительно по желанию.

Оба координатора используют общий локальный диск. Один компьютер с тремя контейнерами
не обеспечивает устойчивость к отказу всей машины; для этого нужны разные узлы и
общее доступное хранилище файлов расчёта. Выбор лидера ZooKeeper и выбор лидера
прикладного координатора — два отдельных механизма.

Справочные материалы: [официальный образ](https://hub.docker.com/_/zookeeper),
[руководство ZooKeeper 3.9.6](https://zookeeper.apache.org/doc/r3.9.6/zookeeperProgrammers.html).

## Как вставить скриншоты в отчёт

Открыть указанные приложения или файлы, выделить читаемый фрагмент через
Win + Shift + S и сохранить PNG в `docs/screenshots/`. Снимки сохранённых журналов
подписывать как вывод выполненного эксперимента. Состояние Docker Desktop на момент
нового снимка может отличаться от исторических ролей; сверять его с подписью.
После нового запуска меняются ID, времена и журналы — тогда нужно обновить и отчёт.

Каждый блок «Место для скриншота» заменить изображением с подписью, например:

```markdown
![Рисунок 3. Начальные роли серверов ZooKeeper](screenshots/03-roles.png)
```

Перед сдачей проверить, что изображения читаемы, открываются на GitHub,
все места для вставки заменены снимками, а в репозитории присутствуют сами журналы.
